# Warehouse Duel — Technical Architecture

1v1 online FPS for Android/iOS. Unity 6.3 LTS + URP + Photon Fusion 2 (Host Mode) + Input System.
This document covers the requirements analysis, packages, architecture, Fusion configuration, folder layout,
milestones and known limitations. It is the reference for every later phase.

---

## 1. Requirements analysis — what is hard, what is easy

| Area | Difficulty | Key risk / decision |
|---|---|---|
| Online 1v1 over different networks | High | Photon Cloud relay handles NAT; **both players must reach the same Photon region** → the room code carries the host's region (§4.3). |
| Authoritative shooting + damage | High | Host validates fire rate, ammo, alive state, match phase; hits use Fusion **lag compensation** (`Runner.LagCompensation.Raycast` + `HitboxRoot`/`Hitbox`). |
| Mobile FPS controls | Medium-high | Multi-touch joystick + look-drag + buttons at the same time; built on uGUI pointer events (one pointer id per finger). |
| Movement prediction | Medium | Local player predicted, host authoritative; Fusion re-simulation means movement code must be deterministic from `[Networked]` state + input. |
| Match flow / timer | Low-medium | One host-owned `MatchManager` with `TickTimer`s; clients only render. |
| Art (low-poly) | Medium (no DCC tool here) | Environment and weapons built from code-generated low-poly meshes and flat-colour URP materials, all as prefabs, so they can be swapped for Blender/CC0 models later. |
| Audio | Medium | Original SFX generated by an editor tool; music from a CC0 source (see §8). |
| iOS | External dependency | Requires a Mac + Xcode + Apple Developer account to build/sign. |

Out of scope for v1 (per the brief): unlock system, more maps, matchmaking with strangers, host migration, accounts/cloud profiles.

| Component | Version | Notes |
|---|---|---|
| Unity Editor | **Unity 6.3 LTS (6000.3.x)** | Current LTS, supported to Dec 2027. 6.0 LTS support ended Oct 2026. |

Fusion 2.1 changes we design around (from the 2.1 release notes):
- `OnInput` must use **`Runner.InputTick`** rather than `Runner.Tick`.
- Reliable data APIs use `ReadOnlySpan<byte>`.
- `HitboxManager` destroys itself unless **Lag Compensation is enabled in `NetworkProjectConfig`**.
- New `ShutdownReason.UnableToMatchmake` / `PhotonCloudTimeout` → handled in the connection UI.
- `StartGameArgs.PlayerUniqueId` keeps the same `PlayerRef` on reconnect → used for temporary-disconnect handling.
- **Asset Serialization must be Force Text.**

Any Fusion API that the docs did not show explicitly is checked against the imported SDK source before it is used in a phase.

## 3. Packages

| Package | Why | How it gets in |
|---|---|---|
| Universal RP | Rendering, mobile quality tiers | Universal 3D template |
| Input System | Touch, keyboard/mouse, UI input module | Universal 3D template (verify in Package Manager) |
| uGUI + TextMesh Pro | All UI | Template; import TMP Essentials |
| Photon Fusion 2.1.4 | Networking | `.unitypackage` from Photon (Assets/Photon) |
| Android Build Support (+OpenJDK, SDK & NDK) | Android builds | Unity Hub module |
| iOS Build Support | Xcode export | Unity Hub module (building needs a Mac) |
| Unity Test Framework | EditMode tests for weapon/match maths | Template default |

Deliberately **not** used: Cinemachine (a first-person camera doesn't need it), Addressables (one map, small build),
the paid Fusion KCC addon. Fusion's built-in `NetworkCharacterController` (wrapping Unity's `CharacterController`) is the
starting point for movement; Phase 3 confirms it is enough for an FPS feel.

**No custom assembly definitions for gameplay code.** Fusion's IL weaver processes `Assembly-CSharp` by default;
putting `NetworkBehaviour`s in custom asmdefs requires registering each one in `NetworkProjectConfig > Assemblies To Weave`.
Keeping game code in the default assembly removes that failure mode. It can be split later if compile times grow.

## 4. Architecture

### 4.1 Layers

```
┌────────────────────────── Presentation (all peers) ──────────────────────────┐
│ UI (menus, lobby, HUD, results) · camera · VFX/SFX pools · view-model weapon  │
│ reads networked state in Render(); never decides outcomes                     │
├────────────────────────── Simulation (Fusion tick) ──────────────────────────┤
│ PlayerMotor · WeaponController · Health · MatchManager · RoomState           │
│ FixedUpdateNetwork(); runs predicted on input authority, authoritative on host│
├────────────────────────── Session / transport ───────────────────────────────┤
│ SessionService (NetworkRunner lifecycle, room codes, regions, callbacks)      │
├────────────────────────── Data ──────────────────────────────────────────────┤
│ WeaponDefinition SO · MatchRules SO · PlayerProfile (PlayerPrefs) · Settings  │
└───────────────────────────────────────────────────────────────────────────────┘
```

Rule: **outcomes (damage, kills, deaths, timer, winner) are written only where `HasStateAuthority` is true.**
Code never checks "am I the host" — it checks state authority or `Runner.IsServer`. That makes the switch to a
dedicated server (`GameMode.Server`) a change in how the session is started, not a gameplay rewrite.

### 4.2 Scenes and flow

| Build index | Scene | Networked? | Purpose |
|---|---|---|---|
| 0 | SplashScreen | No | Logo, loading, → MainMenu |
| 1 | MainMenu | No | Name, profile, settings, Create/Join room. Starts the `NetworkRunner`. |
| 2 | Lobby | Yes (host loads it) | Names, connection, weapon choice, ready, host Start |
| 3 | WarehouseMap | Yes (host loads it) | Match, HUD, results |

```
Splash → MainMenu ──Create──► StartGame(Host, Scene=Lobby) ─┐
                  └─Join────► StartGame(Client, code)  ──────┴─► Lobby ──host Start──► WarehouseMap
WarehouseMap results: Play Again (host resets match in place) · Return to Lobby (host Runner.LoadScene(Lobby))
                      · Main Menu (Runner.Shutdown → MainMenu)
```

Scene order is part of the network contract (`SceneRef.FromIndex`), so it is set by the setup tool, never by hand.

### 4.3 Session, room codes and regions

- `SessionService` (non-networked, lives across scenes) owns the `NetworkRunner`, implements `INetworkRunnerCallbacks`,
  and exposes events to the UI: `StatusChanged`, `PlayerJoined/Left`, `Failed(reason)`.
- **Create Room:** generate a 5-character code from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no 0/O/1/I/L to avoid misreads),
  `StartGame(GameMode.Host, SessionName = code, PlayerCount = 2, IsVisible = false)`. If the session name is taken, retry with a new code.
- **Region in the code:** Photon sessions exist per region, and two phones on different networks can pick different "best" regions.
  After the host connects, its region (from the runner's session info) is appended to the code as one character
  (e.g. `K7QPM-E` → `eu`). The joiner decodes it and connects with that region pinned, so the code always resolves.
- **Join Room:** check the code format locally first, then `StartGame(GameMode.Client, SessionName = code, region pinned)`.
  `GameNotFound` → "Room not found", `GameIsFull` → "Room is full", timeouts → "Connection failed, retry".
- Capacity is enforced twice: `PlayerCount = 2` in Photon, and the host rejects a third `PlayerRef` defensively.

### 4.4 Networked objects and who owns what

| Object | Spawned by | Key `[Networked]` state |
|---|---|---|
| `RoomState` (persists across scenes) | Host on session start | per player: name, selected weapon, ready, connected, kills, deaths |
| `MatchManager` (WarehouseMap) | Host | phase (`Countdown/Playing/Ended/Aborted`), `TickTimer` countdown & match, result (winner `PlayerRef` / draw) |
| `PlayerCharacter` (one per player) | Host, input authority = that player | position/velocity (NCC), yaw/pitch, health, alive, respawn timer, spawn-protection timer |
| `WeaponController` (on the player) | — | current weapon, ammo per weapon, reload timer, fire cooldown timer, shot counter, recent-impact ring buffer |

Player names, weapon choices, ready flags and rematch/lobby requests are sent by clients as **Fusion reliable data**
to the host (`RoomState.Request*` → `SessionService.OnReliableDataReceived` → `RoomState.HandleRequest`); the host
validates them before writing `RoomState`. `[Rpc]` methods are deliberately not used: in Fusion 2.1 the woven RPC code
calls an internal runtime method that Mono builds (Unity Editor, Windows) reject with `MethodAccessException`.

### 4.5 Input

```csharp
struct PlayerNetworkInput : INetworkInput {
    Vector2 Move;            // joystick / WASD, clamped to unit circle
    Vector2 Look;            // absolute yaw/pitch in degrees (robust to dropped inputs and resimulation)
    NetworkButtons Buttons;  // Fire, Aim, Reload, Jump, Sprint
    byte WeaponSlot;         // requested weapon (0-3), host validates
}
```
Input sources (`TouchInputSource`, `KeyboardMouseInputSource`) feed one `LocalInputCollector`, which `SessionService.OnInput`
reads (stamped with `Runner.InputTick`).

### 4.6 Shooting, damage, kills (authoritative)

1. Input authority predicts the shot locally for instant muzzle flash and recoil (presentation only).
2. On the host's `FixedUpdateNetwork`, `WeaponController` validates: match is `Playing`, shooter alive, not reloading,
   cooldown expired, ammo > 0, weapon owned. Otherwise the shot does not happen.
3. Host casts `Runner.LagCompensation.Raycast(...)` from the shooter's eye along the input's look direction
   (one ray per pellet for the shotgun, using spread seeded from the tick so prediction matches), against hitboxes + environment.
4. Damage = weapon damage × range falloff × hitbox multiplier (head/body). Target under spawn protection takes none.
5. `Health.ApplyDamage` runs only with state authority. The `alive → dead` transition happens exactly once and
   is the only place a kill is credited (`RoomState.AddKill(killer)`), so kills cannot be double-counted.
6. Death → respawn `TickTimer` (3 s) → host teleports to that player's spawn point, health 100, ammo reset, spawn protection 2 s.
7. All peers render impacts and muzzle flashes from the networked shot counter + impact ring buffer (`ChangeDetector` in `Render`),
   using pooled effects.

### 4.7 Match

`MatchManager` (host-written, everyone-read): `WaitingForPlayers → Countdown (3 s) → Playing (180 s TickTimer) → Ended`.
Clients show `RemainingTime(Runner)` from the same `TickTimer`, so both phones show the same clock.
At zero: movement/shooting disabled by phase check in simulation; winner = more kills, equal = draw; result written once.
**Play Again:** host resets kills, respawns both, restarts the countdown. **Return to Lobby:** host loads Lobby.

### 4.8 Disconnections

| Event | Behaviour |
|---|---|
| Client drops during match | The match ends immediately as a forfeit win for the remaining player ("Opponent left"); they can return to the lobby or menu. (Pause-and-rejoin was considered but not built in v1.) |
| Host drops / quits | Client's runner shuts down → "Host left the match" → back to main menu. (No host migration in v1.) |
| Local network loss | `OnDisconnectedFromServer` / `OnShutdown` reason shown; button returns to the main menu. |
| Join failures | Mapped from `ShutdownReason` to readable messages (§4.3). |

### 4.9 Dedicated-server readiness

- Gameplay checks `HasStateAuthority` / `Runner.IsServer`, never `IsHost` or "local player 0".
- The host's own player is spawned through the same `OnPlayerJoined` path as the remote player.
- `SessionService.StartAsHost` is the only place `GameMode.Host` appears; a `StartAsServer` / `JoinServerSession` pair can be added later.

### 4.10 Performance budget (mid-range Android)

- Target 60 FPS, 30 FPS fallback via the settings frame-rate cap and the "Mobile" URP quality tier.
- One shadow-casting directional light; warehouse lamps baked or unshadowed; baked GI for the static map.
- Shared materials (GPU instancing / SRP Batcher), < 150 draw calls, combined static geometry, occlusion culling bake.
- Pooled VFX, SFX sources and impact decals; no `Instantiate`/`Destroy` during a match.
- Fusion tick rate 60, 2 players → tiny state; input sent every tick.

## 5. Fusion configuration

1. Photon dashboard → **Create a new app** → type *Multiplayer Game* → SDK **Fusion** / version **Fusion 2** → copy the App ID.
2. Import the Fusion 2.1.4 `.unitypackage` into the project (everything goes under `Assets/Photon`).
3. Fusion Hub (opens after import, or **Tools > Fusion > Fusion Hub**) → paste the App ID.
4. Leave **Fixed Region empty** (regions come from the room code).
5. Phase 5 sets in `NetworkProjectConfig`: **Lag Compensation enabled** (required for hitboxes), tick rate 60,
   and registers the player prefab. Phase 1 only checks that the SDK, config and App ID are present.

Free Photon plan: 20 CCU, enough for development and friend testing.

## 7. Milestones

Each phase ends with a test checklist that has to pass before the next phase starts.

| Phase | Deliverables | Done when |
|---|---|---|
| **1 Foundation** | Project from the URP template, Fusion imported, App ID, settings, layers, folders, 4 scenes, build list, validator | Validator shows 0 errors; Play from Splash reaches MainMenu |
| **2 Warehouse** | Code-generated modular low-poly kit (walls, floor, containers, crates, barrels, shelves, machinery, pillars, catwalk), lighting, colliders, 2 mirrored spawns, boundary, kill-floor safety net | Walk the whole map with a debug fly/walk camera; no holes or exits |
| **3 FPS player** | `PlayerCharacter` as a Fusion `NetworkBehaviour` run in **`GameMode.Single`** for local testing; movement, sprint, jump, look, touch + keyboard/mouse controls | Movement feels right in the Editor and on one phone |
| **4 Weapons** | `WeaponDefinition` SOs ×4, fire modes, spread/pellets, recoil, reload, ammo, switching, pooled VFX/SFX, view-models | All 4 weapons usable in single mode |
| **5 Multiplayer** | `SessionService`, room codes + region, join errors, Lobby + `RoomState`, player spawning, lag-compensated authoritative hits, health, kills | Two phones on different networks see, shoot and kill each other |
| **6 Match** | Countdown, 180 s timer, respawn + protection, scoring, results, play again / lobby / menu, disconnect handling | Full match end-to-end; both phones show the same result |
| **7 UI & polish** | Main menu, profile, settings (volumes, sensitivities, quality, layout, FPS cap), HUD, audio, juice | Every screen in the brief works on 16:9, 20:9 and 4:3 |
| **8 Test & build** | Android APK/AAB, iOS Xcode export, profiling, bug fixing | Acceptance criteria in the brief all pass on devices |

Phases 3–4 build the player directly as Fusion network code and test it in Fusion's single-player mode. Writing an offline
controller first and rewriting it for networking in Phase 5 would duplicate the work. `GameMode.Single` is only a test
harness; Phase 5 tests real multiplayer across two devices.

## 8. Limitations and dependencies

1. **No Unity Editor in the authoring environment.** Code is written against documented APIs but compiled and run only on
   your machine. Every phase includes a validator or test list; Console errors you report back get fixed first.
2. **iOS** builds need macOS + Xcode + an Apple Developer account. On Windows we can configure and export, not build or sign.
3. **Photon account + App ID** must be created by you (it is tied to your account). Free tier: 20 concurrent users.
4. **Art:** no Blender here. Models are generated in-engine as low-poly meshes with flat-colour materials, organised as prefabs so
   they can be swapped. Animated, rigged characters need external assets; recommended CC0 sources: **Quaternius** (animated
   low-poly characters and guns), **Kenney** (Blaster Kit, prototype kits). The remote player uses procedural animation
   (lean, bob, weapon sway, death fall) until rigged models are added.
5. **Audio:** SFX are synthesised by an editor tool, so they are original and license-free. Music needs a CC0/licensed track
   (e.g. from Kenney or OpenGameArt CC0); a placeholder generated loop is provided.
6. **Host advantage:** in Host Mode the host has zero latency. Lag compensation makes hits fair from the shooter's view;
   a dedicated server (§4.9) removes the asymmetry later.
7. **No host migration in v1:** if the host quits, the match ends for the other player.
8. **Two-device testing** across different networks has to be done by you; Phase 5 includes a scripted test plan.
